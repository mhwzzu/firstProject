# Atlas Noir 完整产品升级设计

日期：2026-09-11  
状态：待用户审阅  
目标分支：`codex/develop`  
产品：两个人的漫游簿

## 1. 决策摘要

本轮将现有“推荐 Demo”升级为面向两个人、可以持续使用的私密出行与共同回忆产品。核心价值闭环为：

`表达当下需求 → 获取实时灵感 → 地图核实与比较 → 形成可执行计划 → 出发中轻量陪伴 → 沉淀足迹与回忆 → 学习双方偏好 → 下一次推荐更准确`

产品采用已经确认的 A「Atlas Noir / 夜幕地图」视觉方向：深色地图为主舞台、酸橙色作为关键行动与路线强调、信息层克制、具备旅行编辑感和精密工具感，不使用大面积霓虹或装饰性赛博元素。

本次不是只换皮。一级导航、领域数据、外部服务、推荐闭环和回忆呈现同时升级。

## 2. 产品边界与原则

### 2.1 用户与使用场景

- 初始目标是一个双人私密空间，每位成员有独立账户与独立偏好信号。
- 主要场景包括“今天下班后”“这个周末”“未来某个日期”“一次已经确定目的地的路线安排”。
- 不引入公开社区、陌生人社交、排行榜或胜负式投票。
- 产品应能在没有外部内容服务或定位权限时降级运行，但必须清楚说明数据状态。

### 2.2 设计原则

1. **先替用户缩小选择，再展示资料。** 默认提供少量有明显差异的可执行方案，不制造新的信息焦虑。
2. **地图是决策底座。** 推荐、心愿、计划和足迹都能在地图上落点。
3. **事实与灵感分离。** 高德负责地点、坐标、路线和天气；博查发现公开内容线索。内容摘要不能覆盖地图事实。
4. **双方信号独立。** 心动、跳过、到访和评分按账户记录，系统在后台寻找共同区间，不展示输赢。
5. **自动化优先。** 不要求用户手工保存第三方链接或维护攻略库。
6. **可解释、可纠正。** 用户能看到推荐理由、来源和影响推荐的偏好，并能修改或重置。
7. **完成不是终点。** 行程结束后自动生成可在足迹地图、时间线和相册中找到的回忆草稿。

## 3. 信息架构

产品固定为四个一级入口。桌面端使用左侧窄导航栏，移动端使用底部悬浮导航。

| 入口 | 用户问题 | 核心能力 |
| --- | --- | --- |
| 下一次 | 我们现在或下周末去哪里？ | 自然语言需求、实时推荐、地图、天气、路线、证据、计划 |
| 心愿 | 我们曾经对哪些地方有感觉？ | 独立心动、共同心动、季节提醒、心愿地图 |
| 足迹 | 我们一起去过哪里、留下了什么？ | 足迹地图、时间线、相册、故事卡和年度回顾 |
| 我们 | 系统如何理解两个人，服务是否正常？ | 双方偏好、关系日历、数据源诊断、隐私和本地配置 |

地图不再作为孤立的一级入口，而是贯穿“下一次、心愿、足迹”的空间载体。

## 4. “下一次”决策体验

### 4.1 输入

首页首屏提供自然语言输入，示例：“下周六想看秋景，不走太多路，晚上吃点热乎的”。系统解析并展示可编辑条件：

- 出发日期与可用时段；
- 当前定位、常驻城市或手动出发点；
- 交通方式和最大通勤时间；
- 总预算或人均预算；
- 活动强度、人群接受度和室内/户外倾向；
- 用户临时关键词和硬性排除项。

用户可修改单个条件，并执行“只换餐厅”“更近一些”“更省钱”“不想走路”“避开人群”“按天气重排”等局部更新，不必重新填写全部内容。

### 4.2 结果结构

一次推荐返回 3～6 个候选，默认突出三种策略：

- 最推荐：综合匹配度最高；
- 更轻松：更近、更少排队或更少步行；
- 更惊喜：在没有触碰明确禁忌的前提下探索新类型。

候选详情必须包含：

- 真实名称、地址、坐标和地点类型；
- 与选定出发点的距离和预计通勤时间；
- 计划日期的天气适配结论；
- 预计停留时长和预算区间；
- 双方偏好匹配原因；
- 近期公开内容证据、发布时间和原链接；
- 信息更新时间、可用性与降级状态；
- 心动、跳过、加入计划、查看路线和查看替代项。

### 4.3 推荐反馈

- 心动：记录当前账号的强正向信号，并加入心愿。
- 暂时跳过：降低当前情境下同类候选权重，不永久拉黑。
- 不喜欢这一类：记录可撤销的长期负向信号。
- 加入计划：强正向信号，进入路线编辑器。
- 实际到访与行后反馈：长期权重最高。

“换一批”使用当前条件产生新快照；“更新近期灵感”强制刷新内容证据；两者语义不得混淆。

## 5. 地图能力

### 5.1 地图图层

- 当前推荐；
- 心愿与共同心动；
- 已纳入计划；
- 已去足迹；
- 当前路线和顺路替代项。

图层可独立开关，并支持城市、日期、距离、类别、季节和成员信号筛选。

### 5.2 地图交互

- 使用本次定位、常驻地点或手动选点；
- 以任一成员的位置为中心；
- 计算两个人中间区域；
- 按 15/30/45/60 分钟通勤圈筛选；
- 在可见地图范围或圈选范围内重新推荐；
- 点击标点与右侧候选详情双向联动；
- 沿当前路线搜索餐厅、咖啡馆、室内备选和停车点；
- 查看驾车、步行和公共交通路线；
- 从足迹标点直接打开对应回忆。

浏览器拒绝定位时，产品使用已选择城市或常驻地点，明确显示“按城市估算”，不伪装成精确距离。

## 6. 天气卡片与天气详情

### 6.1 摘要卡

顶部天气卡至少展示：城市、当前天气、温度、计划日期的天气趋势和“是否适合当前计划”。卡片始终可点击。

### 6.2 详情面板

详情以抽屉或浮层打开，包含：

- 当日分时天气和未来数日预报；
- 最高/最低温度、风力和降水提示；
- 户外活动适宜结论；
- 推荐出发时段；
- 穿衣、雨具和傍晚温差提示；
- 当前计划中受天气影响的地点；
- 一键按天气重排；
- 一键切换室内或雨天备选。

如果高德只返回有限字段，界面只展示可以验证的数据；穿衣和适宜性是规则推导结论，应以“建议”表达，不能伪装成原始天气事实。

### 6.3 变化处理

计划日期临近且天气发生明显变化时，系统在首页和计划中显示非阻断提醒，并给出可以一键应用的替代方案。天气服务失败时展示最近成功时间和手动重试，不使用虚构数据。

## 7. 内容发现与推荐证据

### 7.1 博查接入

博查 Web Search API 是首选通用发现提供方。后端使用服务端凭证调用，按城市、季节、日期和用户情境生成针对小红书、抖音、微博和知乎公开索引页面的查询。

统一 `ContentDiscoveryProvider` 接口继续保留，博查成为默认实现；Brave 适配器可以作为未启用的备用实现，不再出现在主流程说明中。

### 7.2 数据加工

后端对发现结果执行：

1. URL、标题指纹和相似内容去重；
2. 平台、标题、短摘要、发布时间、发现时间和原链接规范化；
3. 地点关键词提取；
4. 使用高德 POI 对地点名称和坐标进行核验；
5. 将多来源内容聚合到真实地点；
6. 对时效性、来源多样性、地点可靠性和偏好匹配评分；
7. 只向前端返回必要摘要和跳转链接。

### 7.3 合规边界

- 不绕过登录、验证码、访问频率限制或设备校验；
- 不使用个人 Cookie；
- 不保存或重新托管第三方完整正文、视频和图片；
- 不将搜索摘要当作价格、营业时间、路线或天气事实；
- 每条证据显示平台、标题、时间、短摘要和原链接；
- 外部内容作为不可信文本处理，前后端均不得将其执行为 HTML 或指令。

## 8. 心愿

### 8.1 状态

每个账号独立记录：心动、想去、暂时无感、去过还想去，以及可选的惊喜收藏。双方都产生正向信号时显示“共同心动”，不显示票数或输赢。

### 8.2 浏览方式

- 心愿地图；
- 共同心动、我的心愿、对方愿意分享的心愿；
- 按城市、类型、季节、距离、预算和保存时间筛选；
- 即将过季、天气正合适和最近有新内容的智能提醒；
- 从任意心愿直接生成一次计划。

## 9. 计划与出发中

### 9.1 计划编辑器

计划包含日期、出发时间、集合地点、交通方式、地点顺序、停留时长、预算、备注、预约信息和雨天方案。

支持：

- 拖动调整停靠点；
- 重新计算路线和总时间；
- 只替换某一站；
- 沿路线添加地点；
- 推迟出发或压缩时长；
- 查看天气影响；
- 生成可复制的行程摘要；
- 保存为可复用模板。

### 9.2 今天模式

计划日期当天提供轻量状态页：当前下一站、一键导航、预计到达、营业与天气提醒、快速照片/文字/消费记录、跳过当前站和附近替代项。

## 10. 足迹与回忆

### 10.1 回忆生成

行程结束后自动创建回忆草稿，带入计划日期、路线、地点、当日天气和成员。用户只需补充任意轻量内容：照片、短句、喜欢的一站、评分、实际花费或“下次还想来”。

### 10.2 足迹产品形态

- 足迹地图：按城市、年份、季节、类别和成员筛选；
- 时间线：按一次约会或旅行成组展示；
- 相册：按行程、城市、年份和季节浏览；
- 故事卡：组合路线、天气、照片与文字；
- 月度/年度回顾：统计共同地点、城市、照片和出行主题；
- 去年今天、很久没做过和曾经想再去的轻量提醒。

任何“完成计划”动作之后，界面必须明确展示回忆去向，并提供“立即查看足迹”。

## 11. 双方偏好与“我们”

### 11.1 偏好来源

- 明确偏好：活动类型、饮食忌口、预算、距离、交通、人群、作息和强度；
- 行为偏好：打开、心动、跳过、加入计划、完成、评分和再次到访；
- 情境偏好：工作日晚间、周末、雨天、纪念日和最近活动重复度。

### 11.2 用户控制

用户能查看“系统为什么认为我喜欢这些”、修改或删除单项推断、暂停学习以及重置某类历史。另一位成员的私有偏好由其本人控制。

### 11.3 关系日历

提供纪念日、季节愿望、下一次值得庆祝的日期、随机约会提案和去年今天；不扩展为公开情侣社交产品。

## 12. 视觉与交互系统

### 12.1 设计令牌

- 页面背景：`#0B0E11`；
- 主表面：`#111619`；
- 主强调色：`#C8FF64`；
- 主文字：`#EDF2ED`；
- 次文字：`#78847E`；
- 边框：低透明白色，避免重描边；
- 圆角：卡片 16～20px，主要容器 24～28px；
- 阴影：大范围低透明黑色，不使用彩色外发光堆叠。

### 12.2 交互反馈

- 地图标点、候选列表和详情保持选中状态同步；
- 重要提交使用短时 Toast，并在目标页面保留可验证结果；
- 加载使用骨架与阶段文案，如“正在核实地点”“正在计算路线”，避免无信息旋转图标；
- 仅对路线绘制、抽屉进入、卡片切换和状态确认使用 160～280ms 动效；
- 支持键盘焦点、减少动态效果偏好和至少 AA 级文本对比度。

### 12.3 响应式

- 桌面：左侧导航、中央地图、右侧详情三栏；
- 平板：左侧导航、地图与底部详情；
- 手机：底部导航、全屏地图、可拖动详情面板；
- 移动端不得把桌面三栏简单压缩，关键行动固定在拇指可达区域。

## 13. 本地配置与密钥安全

### 13.1 本地配置

仓库提供不含密钥的 `.env.local.example`。用户在仓库根目录创建 `.env.local`，后端启动时自动读取，无需每次在 PowerShell 设置环境变量。

建议变量：

```properties
AMAP_KEY=
BOCHA_API_KEY=
BOCHA_API_BASE_URL=https://api.bochaai.com/v1
DISCOVERY_ENABLED=true
DISCOVERY_CACHE_MINUTES=60
DISCOVERY_RESULT_LIMIT=3
```

`.env.local` 必须被 Git 忽略；前端构建不得接收这些变量。应用日志不得打印完整凭证、Authorization 头或外部响应中的敏感字段。

### 13.2 设置页

设置页只展示“已配置/未配置”、连接测试结果、最近成功时间和掩码后的少量尾部字符。修改密钥属于本地管理能力，默认不通过普通业务 API 返回密钥原文。

由于开发阶段凭证曾通过对话提供，生产发布前应重新生成生产密钥，并为服务端 Key 配置平台允许的配额和来源限制。

## 14. 数据与接口演进

后端保留现有账户、双人空间、推荐和计划数据，并增量演进：

- `PlaceSignal`：成员独立的心动、跳过、不喜欢、到访和评分；
- `RecommendationSnapshot`：输入条件、规则版本、来源状态和生成时间；
- `RecommendationCandidate`：真实 POI、评分、距离、天气结论和证据；
- `Journey` / `JourneyStop`：可排序计划及交通、时间和预算；
- `MemoryAlbum` / `MemoryItem`：一次行程及照片、文字、消费和反馈；
- `PreferenceInference`：可解释、可撤销的行为偏好；
- `DiscoveryRecord`：最小化保存的公开内容证据。

主要 API 分组：

- `/api/v1/recommendations`：生成、刷新、局部调整和候选详情；
- `/api/v1/map`：地点、路线、通勤圈、天气与附近替代项；
- `/api/v1/wishes`：心愿状态、共同心动和提醒；
- `/api/v1/journeys`：计划、停靠点、重排和今天模式；
- `/api/v1/memories`：回忆草稿、足迹、时间线和相册；
- `/api/v1/preferences`：明确偏好、推断项和重置；
- `/api/v1/integrations/status`：不含密钥的连接状态与诊断。

所有空间数据读取和写入必须验证当前账号是该双人空间成员。

## 15. 异常、空状态与性能

- 博查失败：继续使用已缓存证据和高德候选，标记证据更新时间；
- 高德地点失败：不能将未核实内容作为可导航候选；
- 天气失败：候选仍可展示，但天气适宜性明确未知；
- 单一平台无结果：不影响其他来源；
- 全部无结果：解释原因，保留条件并给出扩大距离/时间的建议；
- 外部调用设定超时、有限重试、缓存和并发上限；
- 首屏先返回结构与缓存候选，实时证据可分阶段更新；
- 不因刷新按钮重复点击造成并发请求风暴。

## 16. 分阶段实现

### 阶段一：可用的完整主闭环

- Atlas Noir 响应式应用壳和四区导航；
- 博查默认内容发现、高德地点/路线/天气；
- 可点击天气详情和天气重排入口；
- 自然语言/筛选条件、候选地图联动与来源证据；
- 心动、跳过、加入计划和可编辑计划；
- 心愿列表与心愿地图；
- 足迹地图、时间线和回忆草稿；
- 双方偏好与集成诊断；
- 根目录 `.env.local` 自动加载。

### 阶段二：体验加深

- 今天模式、附近替代项与更完整交通方式；
- 照片持久化、相册浏览和故事卡；
- 偏好推断解释与关系日历；
- 后台定时发现、提醒和月度/年度回顾。

阶段一必须是可使用产品，阶段二是纵深能力，不得用不可点击占位卡代替阶段一核心流程。

## 17. 验收标准

1. 新用户完成登录和创建/加入双人空间后，能够进入四区产品壳，不再看到旧版三项导航。
2. 用户能输入一句自然语言并获得 3～6 个带真实地图位置、距离/路线、天气结论和近期证据的候选。
3. 天气摘要卡可点击进入分时/未来天气详情，并能触发“按天气重排”或选择备选方案。
4. 用户能对地点心动、跳过、加入计划；刷新页面后状态仍存在，并影响后续推荐。
5. 用户能编辑包含多个停靠点的计划，完成后生成可在足迹地图和时间线找到的回忆草稿。
6. 心愿、推荐、计划和足迹能在地图上区分显示并打开详情。
7. 博查、高德、定位任一不可用时都有准确降级状态，核心界面不白屏，不伪造实时数据。
8. 根目录 `.env.local` 能被后端自动读取，密钥不会进入前端产物、日志和 Git。
9. 桌面与移动视口完成响应式检查，关键路径可以通过键盘操作。
10. 后端测试、前端生产构建和关键业务流自动化测试全部通过。

## 18. 非目标

- 绕过第三方平台登录或反自动化能力进行直接抓取；
- 复制或托管第三方完整内容；
- 面向陌生用户的公开社区与投票；
- 第一阶段实现酒店、门票或餐厅的商业交易闭环；
- 用无法工作的按钮或假数据冒充已完成能力。

## 19. 实施顺序

1. 安全配置与博查适配器；
2. 前端应用壳、设计令牌和路由状态；
3. 推荐聚合、地图与天气详情；
4. 心愿与成员信号；
5. 计划编辑和完成闭环；
6. 足迹地图、时间线和回忆；
7. 偏好与集成诊断；
8. 响应式、无障碍、异常态与性能收尾；
9. 全量测试、分支提交并推送 `codex/develop` 和 `test`。
