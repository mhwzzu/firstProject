# 双核心生活产品：自动内容发现与推荐设计

日期：2026-09-11  
状态：已批准，进入实现  
目标分支：`codex/develop`

## 1. 产品目标

“两个人的漫游簿”从依赖用户收藏与手工录入的 Demo，升级为会主动寻找近期灵感、解释推荐依据、协助两个人完成周末决策，并在到访后沉淀偏好的私密生活产品。

1.0 的首要价值不是建立攻略数据库，而是形成闭环：

`情境与偏好 → 自动发现外部内容 → 地图地点校验 → 个性化推荐 → 心动/跳过/计划 → 到访回忆 → 下一次推荐更准确`

## 2. 信息架构

产品保持四个一级入口：

- 下一次：输入一句话，查看动态推荐、地图、距离、天气、来源证据和路线。
- 心愿：汇总双方各自标记的心动地点，不使用公开投票或胜负式比较。
- 足迹：完成行程后形成地图落点、时间线、照片、感受、评分和消费。
- 我们：分别管理个人偏好、双人空间和数据源状态。

本次最小交付优先完成“下一次”的自动发现闭环，并为后续三个入口建立稳定数据结构。

## 3. 自动发现策略

### 3.1 来源组合

- 知乎：官方内容搜索 API，凭证可用时启用。
- 微博：官方搜索/趋势能力，凭证或服务可用时启用。
- 抖音：官方视频、POI 能力，权限可用时启用。
- 小红书：公开搜索索引发现，取得平台合作能力后替换为官方适配器。
- 通用搜索索引：通过受支持的 Web Search API 以 `site:` 查询发现四个平台公开索引的标题、短摘要、链接和时间。
- 高德：地点搜索、坐标、路线和天气的事实底座。

初版提供可插拔 `ContentDiscoveryProvider`，首个生产可用实现为搜索索引适配器；未配置凭证时必须明确显示降级状态，不伪造实时抓取结果。

### 3.2 合规与稳定性边界

- 不绕过登录、验证码、设备指纹、访问频控或平台权限。
- 不使用用户个人 Cookie 抓取内容。
- 不保存整篇第三方正文、视频或原始图片。
- 保存必要的标题、短摘要、原文链接、平台、发布时间、发现时间和内容指纹。
- 原文通过新窗口跳转回来源平台。
- 单一来源失败不阻塞地图和其他来源。

### 3.3 更新模型

- 普通推荐首先返回可用的地图候选。
- “更新近期攻略”发起强制增量发现，绕过短期缓存。
- 相同城市与查询的发现结果短期缓存，减少成本和限流风险。
- 结果标记生成时间、已连接来源、不可用来源和是否处于降级模式。
- 后续增加后台调度：常驻城市每 6 小时，节假日前每 2～3 小时。

## 4. 推荐流水线

1. `QueryPlanner` 将城市、季节、日期、天气、提示词、标签、预算、车程和双方偏好转换成 2～4 个检索主题。
2. 多个 `ContentDiscoveryProvider` 返回统一的 `DiscoveredContent`。
3. 规范化标题、摘要、来源、时间与 URL，并按 URL/标题指纹去重。
4. 从内容标题与摘要提取地点提示词。
5. 使用高德 POI 搜索将提示词解析为真实地点；不能可靠落点的内容仅可作为灵感证据，不进入主要候选。
6. 聚合同一地点的多来源证据。
7. 综合双方偏好、个人行为、天气季节、距离预算、新鲜度与来源多样性排序。
8. 输出候选地点、解释、路线和 1～4 条证据。

## 5. 推荐与偏好学习

双方使用各自账号产生独立信号：

- 心动：提高该用户对地点类别、主题和区域的偏好权重。
- 跳过：降低相似内容的短期曝光，不永久拉黑。
- 加入计划：作为强正向信号。
- 实际到访与评分：作为最强长期信号。

共同排序不展示投票比较，而是综合：

- 两个人都可能接受的“共同区间”。
- 一方强烈喜欢且另一方没有明确排斥的探索机会。
- 最近重复过多的类别降权。
- 适度加入新颖地点，避免越用越单一。

本次实现至少把历史 `WANT` 与 `SKIP` 纳入候选分数，并继续保留每个账号的独立记录。

## 6. 接口与数据模型

### 6.1 新数据

`DiscoveryRecord`

- `id`, `spaceId`, `provider`, `platform`
- `queryText`, `title`, `snippet`, `sourceUrl`
- `publishedAt`, `discoveredAt`, `fingerprint`
- `placeKeyword`, `status`

`RecommendationEvidence`

- `id`, `candidateId`, `platform`
- `title`, `summary`, `sourceUrl`
- `publishedAt`, `discoveredAt`

### 6.2 推荐接口

`GET /api/v1/recommendations/today`

`GET /api/v1/recommendations/weekend`

新增参数：

- `refresh=true`：强制发起近期内容更新。
- 其余参数保持向后兼容。

响应新增：

- `discoveryStatus`：`LIVE`、`PARTIAL` 或 `DEGRADED`。
- `connectedSources`、`unavailableSources`。
- `refreshedAt`。
- 候选中的 `evidence[]`。

## 7. 前端交互

- 主按钮为“帮我们决定”，保留自然语言和可选筛选条件。
- 增加“换一批”和“更新近期攻略”两个明确动作。
- 推荐区展示“正在读取近期灵感 / 已更新 / 部分来源不可用”。
- 选中候选后展示来源证据卡：平台、标题、短摘要、日期和“查看原文”。
- 没有搜索 API Key 时显示配置引导，不将高德 POI 冒充为社交平台内容。
- 加载、空结果、部分失败、完全降级均有明确状态。

## 8. 配置

初版搜索索引适配器使用 Brave Search API：

- `DISCOVERY_ENABLED=true|false`
- `BRAVE_SEARCH_API_KEY`
- `DISCOVERY_CACHE_MINUTES`，默认 60
- `DISCOVERY_RESULT_LIMIT`，默认每个平台 3 条

后续官方平台适配器使用独立配置，不改变统一领域接口。

## 9. 测试与验收

- 未配置发现服务：推荐仍可用，响应和界面明确为 `DEGRADED`。
- 配置发现服务且返回公开内容：响应包含平台证据和更新时间。
- 任一平台查询失败：其他来源与地图推荐不受影响，状态为 `PARTIAL`。
- `refresh=true` 不使用当前短期缓存。
- 外部标题和摘要不能注入 HTML；前端仅以文本渲染。
- 不同双人空间无法读取彼此的发现记录与候选证据。
- 心动和跳过会影响后续候选排序。
- 后端测试通过，前端生产构建通过。

## 10. 非目标

- 绕过平台认证和反自动化机制。
- 全量、秒级镜像四个平台内容。
- 下载或重新托管第三方视频与图片。
- 在第一批交付中完成多日旅行自动排程、社区和商业化。
