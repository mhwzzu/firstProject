# 双人出行决策助手：产品化设计

日期：2026-09-02
状态：已完成设计，待用户审阅

## 1. 目标与定位

将现有「两个人的漫游簿」从单账号的回忆记录 Demo，升级为手机优先的私密双人出行决策助手。应用必须在没有手动收藏攻略的情况下，主动给出有来源、可解释的地点和旅行建议；两人的共同决策与实际反馈会持续改善后续推荐。

首发版本服务一对情侣或搭档，不做公开内容社区。每位成员拥有独立账户，并通过邀请码加入一个私密双人空间；一人创建空间后邀请另一人加入。多空间关系留待后续版本，不作为首发行为。

核心价值是同时解决两类高频问题：

- **即时决策**：基于常驻城市或授权的位置、当前时间、天气、距离、营业状态、预算和双方偏好，回答“今晚/今天去哪里”。
- **提前规划**：基于出行日期、季节、天气预报、假期、时长、预算和双方偏好，回答“下个周末/假期去哪”。

## 2. 产品边界

### 首发范围

1. 两人独立注册、登录、邀请码加入私密空间。
2. 首次引导采集常驻城市、餐饮/活动偏好、预算、出行半径和旅行偏好；成员可随时修改。
3. 首页呈现两组主动推荐：即时推荐与周末/假期推荐。
4. 候选支持双方独立的想去、跳过、已去和投票反馈；支持加入共同计划。
5. 计划支持日期、预算、地点列表和备注；结束后可以转为回忆和评价。
6. 手机优先的响应式 Web 应用与 PWA 安装能力，桌面端保持完整可用。

### 不在首发范围

- 抓取、复制、缓存小红书或其他第三方内容平台的笔记。
- 公开社区、关注关系、评论流、内容审核、支付或自动下单。
- 没有数据来源的 AI 地点推荐。
- 原生 iOS/Android 客户端。

用户可选地保存外部攻略链接作为个人补充信息；链接从不作为生成推荐或使用产品的前置条件，也不抓取其内容。推荐结果可跳转到地图详情或原始链接。

## 3. 推荐架构

推荐采用“规则优先，大模型增强”的分层架构。

1. **上下文构建器**收集空间、双方显式偏好与行为反馈、日期时间、目标城市、预算、出行半径及用户授权的实时位置。实时位置仅用于本次计算，不保存位置轨迹。
2. **事实提供方**通过正式地图服务提供 POI、地址、距离、路线、营业状态和天气信息；一小套可审查的目的地季节知识库提供旅行候选的基础事实。第三方 API 密钥只保存在后端。
3. **候选与规则评分器**过滤不符合硬约束的地点，按分项得分排序，并输出每个候选的来源、输入、规则版本和评分依据。
4. **大模型增强层**只消费已验证的候选和事实：理解自然语言偏好、生成简洁推荐理由、比较候选、生成可编辑行程草案。它不能新增候选，不能改写营业、价格、天气或交通等事实字段。
5. **共同决策层**记录两人独立反馈，将候选转为计划，再将完成计划转为回忆；反馈进入下一轮评分。

大模型或其服务不可用时，规则推荐必须独立返回，不阻断核心闭环。

## 4. 数据模型

当前 `Memory` 模型保留为历史回忆，逐步迁移至下列职责明确的对象：

| 对象 | 职责 | 关键数据 |
| --- | --- | --- |
| `User` | 独立身份与个人偏好 | 已验证邮箱、密码哈希、状态、预算、饮食与活动偏好 |
| `CoupleSpace` | 私密共享边界 | 名称、默认城市、成员、创建者 |
| `SpaceMembership` | 成员权限与个人空间设置 | 空间角色、加入时间、个人默认城市 |
| `Invite` | 安全地建立双人空间 | 空间、一次性令牌哈希、过期时间、撤销状态、使用者 |
| `Place` | 标准化地点事实 | 外部 POI 标识、名称、类别、坐标、地址、营业与数据来源 |
| `PreferenceProfile` | 显式偏好 | 个人或空间维度的口味、活动、预算、半径、权重 |
| `RecommendationRun` | 可复现推荐快照 | 空间、推荐类型、上下文、规则版本、生成时间、过期时间 |
| `RecommendationCandidate` | 每次推荐的候选及理由 | 地点/目的地、总分、分项得分、过滤原因、事实来源 |
| `CandidateFeedback` | 双人学习信号 | 成员、候选、动作（想去/跳过/已去/投票）、时间、备注 |
| `Plan` / `PlanItem` | 共同约会或旅行计划 | 日期范围、预算、状态、地点、备注、成员决策 |
| `Memory` | 已完成体验的沉淀 | 计划关联、日期、评分、照片/文本/标签、地点 |

所有查询必须带 `CoupleSpace` 成员校验；对象 ID 不能替代授权判断。

## 5. 评分和解释

评分结果必须显示可读原因，并保留机器可读分项用于复现。初始权重是可配置版本化规则，不由模型自行修改。

### 即时推荐（100 分）

| 因素 | 分值 | 说明 |
| --- | ---: | --- |
| 双人偏好匹配 | 30 | 双方共同偏好优先；冲突偏好体现为折中或轮换推荐 |
| 天气与时间适配 | 20 | 雨天/温度/时段、室内外、就餐时段 |
| 距离与可达性 | 20 | 路线时间、出行半径、交通方式 |
| 营业与预算 | 15 | 当前营业、预计人均/总预算 |
| 新鲜度与去重 | 15 | 避免近期已去、已连续推荐或重复 POI |

### 周末/假期推荐（100 分）

| 因素 | 分值 | 说明 |
| --- | ---: | --- |
| 季节与日期适配 | 25 | 目的地最佳季节、节假日与建议出行窗口 |
| 双人偏好匹配 | 25 | 餐饮、自然、人文、节奏等共同偏好 |
| 行程时长与交通 | 20 | 可用天数、路线时间和跨城可达性 |
| 天气与预算 | 15 | 预报、温度、降水和预算约束 |
| 未去过与多样性 | 15 | 规避已去目的地，保持推荐多样性 |

示例解释：“你们都偏好川菜；当前下雨，室内用餐更合适；距离常驻地 1.2 km；目前营业中。” 解释只能引用已保存的候选事实和分项。

## 6. 前后端结构

前端从单一 `App.vue` 演进为按领域划分的 Vue 模块：认证与入驻、空间、推荐首页、候选详情与反馈、计划、回忆、设置。采用路由、可复用 API 客户端、独立状态模块和移动端优先组件；通过 manifest、service worker 和离线提示提供 PWA 能力。

后端按领域拆分 Controller、Service、Repository、DTO 和集成适配器：认证与授权、空间/邀请码、地点与地图、天气、推荐、反馈、计划、回忆。第三方服务通过接口适配器隔离，推荐服务不直接依赖 HTTP 客户端实现。数据库使用 PostgreSQL；H2 仅保留开发与测试体验，生产环境采用迁移脚本管理模式变更。

关键 API 以 `/api/v1` 命名空间组织，至少覆盖：认证、空间成员与邀请码、偏好、即时/旅行推荐、候选反馈、计划、回忆与健康检查。

## 7. 安全、隐私与异常处理

- 使用成熟认证与授权组件；密码采用强单向哈希，不再使用环境变量中的固定明文账号密码。
- Cookie 会话启用安全属性并配置 CSRF 防护；登录端点限流，邀请令牌一次性、可撤销、可过期且仅保存哈希。
- 不保存精确位置历史；显示授权目的，允许拒绝后以常驻城市继续推荐。
- 地图、天气和模型调用均设置超时、重试边界与限流保护。外部事实服务失败时返回最近的缓存/成功快照并注明更新时间；没有可用数据时展示可操作的空状态，而不是伪造推荐。
- 推荐快照包含输入上下文、来源时间、规则版本、候选和评分；敏感偏好不进入日志或大模型提示词的非必要部分。

## 8. 测试与验收

后端测试覆盖：成员隔离、邀请码生命周期、密码与登录安全、规则评分、行为反馈更新、计划状态转换、第三方超时与缓存降级。前端测试覆盖：首次引导、推荐理由、双人投票、计划创建、授权拒绝、慢网与离线提示；端到端测试覆盖两个新用户从注册、入空间、获得推荐、共同决策、完成计划到形成回忆的完整流程。

首发验收条件：

1. 两个新用户可在手机上于数分钟内创建空间并看到带事实来源、更新时间和解释的两类推荐。
2. 任意成员对候选的操作立即反映在空间计划和后续排序中；非成员无法读取或修改任何空间资源。
3. 地图、天气或模型任一依赖失败时，核心界面保持可用并清晰说明降级状态。
4. 候选事实不由大模型凭空生成；每项推荐能追溯到规则版本与数据来源。

## 9. 分阶段交付

**阶段 1：产品地基。** 账号与空间、邀请码、权限隔离、偏好、数据库迁移、移动端基础框架和 PWA。

**阶段 2：可信自动推荐。** 地图/天气适配器、地点标准化、推荐快照与规则评分、首页双轨推荐、缓存与降级。

**阶段 3：共同决策闭环。** 反馈、投票、计划、回忆关联与推荐学习信号。

**阶段 4：模型增强与体验打磨。** 只基于验证候选的解释、比较和行程草案；监控、审计、可观测性和部署加固。

阶段 1 至 3 即构成真正可用的首发版本；阶段 4 不得阻塞其上线。
